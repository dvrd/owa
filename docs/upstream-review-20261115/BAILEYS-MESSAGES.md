## Result

OWA should receive one focused receive-correctness fix now. A second inbound LID discovery improvement has a demonstrated missing code path but should retain an explicit policy/integration question before implementation. No wholesale Baileys upgrade or automatic version bump is justified by these files.

### 1. Ready fix: do not durably classify unsupported encrypted message content as handled

The observed receiver explicitly NACKs `msmsg` with `MissingMessageSecret` at lines 1585–1591. OWA `receive.odin:471–519` loops only through `pkmsg`, `msg` and `skmsg`; every other encrypted child type is skipped. With only `msmsg` (or another unknown `enc` type), it returns a nil payload and no error. `socket_process_message` then calls `socket_message_processed_commit` at `receive.odin:242–244`, recording `.Processed_Message`; normal receipt/ACK handling proceeds. Thus unsupported encrypted content can become durably marked handled without an application message or explicit unsupported-content outcome. This is a static control-flow conclusion, not a claim that botlab has encountered it.

The reference already bypassed `msmsg`, but the observed revision changes its response from ordinary ACK to an explicit negative ACK. OWA's durable success marker makes the local consequence especially relevant to reliability. The issue is independent of implementing the unsupported encryption scheme.

Acceptance for a focused fix:

1. Owned synthetic `msmsg`-only and unknown-`enc` stanzas produce no business event, no `.Processed_Message`/`.Inbox_Message` success record and no successful delivery claim; choose an explicit unsupported-content/NACK result.
2. Match the authoritative `MissingMessageSecret` reason for known `msmsg` only after obtaining the owning constant definition; this review did not fetch that additional file or guess a numeric value.
3. Define mixed supported+unsupported child behavior explicitly; reject ambiguous content rather than silently discarding part of it. Preserve supported pairwise-distribution-before-`skmsg` ordering.
4. Reconnect/replay of the same unsupported stanza remains bounded and does not convert it to success. Valid distribution-only control stanzas still complete normally.
5. Exercise the existing ACK routing fixture with negative/error attributes and persist-failure cases. Current baseline ACK coverage does not include `msmsg` or unknown encrypted content (`rg` found no such fixture).

### 2. Scoped follow-up: learn authenticated inbound PN/LID aliases before choosing session state

The observed receiver extracts `participantAlt`/`remoteJidAlt`, stores an unknown mapping and migrates session state before decrypting (`messages-recv.ts:1607–1628`). OWA resolves an incoming participant through existing mappings (`receive.odin:481`, `addressing.odin:1089`), and has careful mapping/migration implementations with cryptographic identity pin validation (`addressing.odin:1147–1289`). But its receive path never reads `participant_pn`, `sender_pn`, `participant_lid` or `sender_lid`: current mapping ingestion comes from explicit group metadata or pairing flows. An inbound-first alias therefore has no path to connect to already persisted state merely because the server supplies the alternate address. This is a real implementation gap; whether a specific stanza shape is authoritative enough to seed a mapping must be specified, not guessed from an unreviewed helper.

Keep this narrowly scoped investigation before implementation: inspect the owning upstream addressing-context decoder, document exactly which authenticated stanza fields bind the alias/device, then implement a staged alias ingest that reuses OWA's existing conflict and pin checks. Acceptance should cover incoming PN→LID and LID→PN with an existing session before any group-metadata fetch, device suffixes, conflicting aliases, different cryptographic identity pins, persistence failure, duplicate/reconnect delivery and unchanged state on refusal. Do not replace OWA's canonical PN-backed state layout merely because Baileys prefers LID-backed state.
